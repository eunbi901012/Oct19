## User Scenarios & Testing

관리 권한의 실제 역할코드와 인증 방법은 OQ-AUTH-001이다. 아래 행위자는 권한이 승인된 관리 주체라는 전제이며 중앙 관리자 고정 정책이 아니다.

### User Story 1 - 사용자 관리 (Priority: P1)

사용자 관리 화면에서 사용자 조건 검색, 사용자 인사정보 목록 표시, 사용여부·업무 역할 변경 유지를 완성한다. 진입점은 `/admin/users`이며 결과는 서버 재조회에서 검증한다.

**Why this priority**: R0-A 인사·역할의 기반 판정 또는 접근 보호를 우선 검증한다.

**Independent Test**: CMN-FR-001의 fixture만 준비하고 /admin/users에서 교번·성명·소속·직급·재직상태·역할·사용여부 중 하나 이상의 조건으로 검색하면 조건에 맞는 사용자만 표시된다. / 사용자 목록에 보직·퇴직일자·최종 동기화일시를 포함한 명시 항목이 표시된다. / 시스템 사용여부 또는 업무 역할을 변경하고 다시 조회하면 변경값이 유지된다.

**Acceptance Scenarios**:

1. **Given** CMN-FR-001 검증용 데이터와 승인된 접근 조건이 준비되어 있다. **When** `searchUsers`에 원문 조건을 입력하여 조회한다. **Then** 교번·성명·소속·직급·재직상태·역할·사용여부 중 하나 이상의 조건으로 검색하면 조건에 맞는 사용자만 표시된다. (REQ-001, CMN-FR-001-AC-01).
2. **Given** CMN-FR-001 검증용 데이터와 승인된 접근 조건이 준비되어 있다. **When** `searchUsers`에 원문 조건을 입력하여 조회한다. **Then** 사용자 목록에 보직·퇴직일자·최종 동기화일시를 포함한 명시 항목이 표시된다. (REQ-002, CMN-FR-001-AC-02).
3. **Given** CMN-FR-001 검증용 데이터와 승인된 접근 조건이 준비되어 있다. **When** `updateUserSettings`에 해당 편집값을 저장하고 다시 조회한다. **Then** 시스템 사용여부 또는 업무 역할을 변경하고 다시 조회하면 변경값이 유지된다. (REQ-003, CMN-FR-001-AC-03).
4. **Given** CMN-FR-001 검증용 데이터와 승인된 접근 조건이 준비되어 있다. **When** 인사 원천 필드를 포함한 변경 요청을 전송한다. **Then** KORUS 원천 인사정보는 화면과 서버 처리에서 변경할 수 없다. (REQ-004, CMN-FR-001-AC-04).

### User Story 2 - 조직 관리 (Priority: P1)

조직 관리 화면에서 조직 현재 관계 조회, 상위조직 적용기간 저장, 변경 전 조직관계 이력 조회를 완성한다. 진입점은 `/admin/organizations`이며 결과는 서버 재조회에서 검증한다.

**Why this priority**: R0-A 인사·역할의 기반 판정 또는 접근 보호를 우선 검증한다.

**Independent Test**: CMN-FR-002의 fixture만 준비하고 /admin/organizations에서 조직코드로 조회하면 해당 조직의 조직구분과 현재 상위·하위 관계가 표시된다. / 상위조직 변경 시 적용 시작일·종료일과 변경된 상위조직이 함께 저장된다. / 변경 이후에도 변경 전 조직관계와 적용기간을 이력으로 조회할 수 있다.

**Acceptance Scenarios**:

1. **Given** CMN-FR-002 검증용 데이터와 승인된 접근 조건이 준비되어 있다. **When** `getOrganizationRelations`에 원문 조건을 입력하여 조회한다. **Then** 조직코드로 조회하면 해당 조직의 조직구분과 현재 상위·하위 관계가 표시된다. (REQ-005, CMN-FR-002-AC-01).
2. **Given** CMN-FR-002 검증용 데이터와 승인된 접근 조건이 준비되어 있다. **When** `saveOrganizationRelation`에 대상·관계·기간과 해당 기록값을 전송한다. **Then** 상위조직 변경 시 적용 시작일·종료일과 변경된 상위조직이 함께 저장된다. (REQ-006, CMN-FR-002-AC-02).
3. **Given** CMN-FR-002 검증용 데이터와 승인된 접근 조건이 준비되어 있다. **When** 조직코드로 `listOrganizationRelationHistory`를 조회한다. **Then** 변경 이후에도 변경 전 조직관계와 적용기간을 이력으로 조회할 수 있다. (REQ-007, CMN-FR-002-AC-03).
4. **Given** CMN-FR-002 검증용 데이터와 승인된 접근 조건이 준비되어 있다. **When** `saveOrganizationRelation` 호출 전후 관련 참조 행의 값을 비교한다. **Then** 조직구조 변경이 사용자의 소속·보직 또는 역할정보를 직접 변경하지 않는다. (REQ-008, CMN-FR-002-AC-04).

### User Story 3 - 역할 관리 (Priority: P1)

역할 관리 화면에서 역할 정의 저장·재조회를 완성한다. 진입점은 `/admin/roles`이며 결과는 서버 재조회에서 검증한다.

**Why this priority**: R0-A 인사·역할의 기반 판정 또는 접근 보호를 우선 검증한다.

**Independent Test**: CMN-FR-005의 fixture만 준비하고 /admin/roles에서 역할별 목적·부여 기준·데이터 범위 기본값을 저장하고 재조회할 수 있다.

## Success Criteria

### Measurable Outcomes

- 아홉 여정의 원문 AC를 누락 없이 각각 테스트에 연결한다.
- 저장값 재조회·비간섭 snapshot·권한 차단이 각 소유 요구 기준을 충족한다.

## Assumptions

기술 명명·DTO·페이지 인터페이스는 설계 제안이다. 미확인 명확화 답변은 승인된 가정이 아니며 OQ 목록으로 남긴다.

REQ-003/REQ-012/REQ-013/REQ-016의 숨김 식별자 전달은 기술 설계다. 기존 user_id/assignment_id/permission_id는 선택한 응답에서 유지하며, 신규 부여·최초 메뉴 설정만 frontend 내부 UUID를 생성하고 재시도까지 보존한다. 식별자를 사용자 입력란으로 추가하지 않는다. REQ-015의 is_current와 business_roles는 계산 projection이다. REQ-016에서 선택되지 않은 대상은 요청 생략/null·DB NULL·응답 null이며 세 대상을 동시에 필수로 취급하지 않는다. 여러 대상의 허용 조합·권한 우선순위·동일 설정 판정은 OQ-AUTH-001이다. 상세 binding·mutability·DTO는 ui-design.md/data-model.md/contracts/openapi.yaml이 이 결정을 투영한다.
